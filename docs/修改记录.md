# 修改记录

本文件记录**每一次改动改了什么、为什么改**。它的存在有两个理由：

1. `backend/tests/test_default_path_frozen.py` 的约定是：任何落在**默认路径**
   （用户一句澄清都不回答）上的改动，都必须显式重新冻结基线，并在这里说明原因。
   没有这份记录，「重新冻结」就变成了一次静默覆盖。
2. 这个产品的主张是「把约束写进代码，而不是写在文档里靠自觉」。
   一份记录**改了什么、为什么**的文件，是这句话对着自己用的那一遍：
   如果一处改动说不出理由，它就不该发生。

写作约定与 `docs/AI使用与验证记录.md` 相同：每一处代码位置都在写作时打开文件核对过；
每一个数字都来自实跑输出。无法核实的说法不写。

### 四、被替换掉的那条护栏

上一轮放了一条 `test_no_answers_is_byte_identical_to_before`，名字写着
「不回答时输出与既有行为逐字相同」，写法是「**同一份代码**，不传 `answers`
跑一次、传空字典跑一次，两边相等」。**这条断言恒真**：它守住的只是
「两种不传参的写法等价」，而名字承诺的是「与改动前逐字相同」。

后果是实测出来的：澄清功能改掉了两处默认路径上的文案，
而四条例题的结论是交付物的一部分（README、文档、演示视频都引用了它们）。
**当时 216 条测试一条都没红。**

现在改成与一份**检入仓库的基线**比对。基线是这一层唯一的真相来源；任何落在默认路径上的
改动都必须显式重新冻结（`python -m tests.test_default_path_frozen --freeze`）
并写进本文件。「顺手改掉一句措辞」不会再有第二次。

### 八、交付文档的引用核对（一遍机器核对，不是通读）

`docs/AI使用与验证记录.md` 与本文件都写着同一句写作约定：
「每一处代码位置都在写作时打开文件核对过」。这句话是可以被证伪的，
所以把两份文档加 `README.md`、`docs/部署说明.md` 里的引用全抽出来——
`文件:行号`、「符号名」、引号内原文三类——逐条拿到工作树里对了一遍。

**先被证伪的是那句约定自己**。`AI使用与验证记录.md` 开头写着
「文件行号以 `377657e` 为准（2026-09-23 22:35）」。实测：25 处行号引用里，
10 处与 `377657e` 对不上，却**逐条与更早的 `a3acee6` 吻合**。
也就是说，那个基准是当时顺手写下的，不是核对出来的——
一份通篇在记录「凭据要真」的文件，给自己发了一处假凭据。

处理办法不是把行号逐个改准（下一次提交又会漂），而是**换掉引用的形式**：
行号全部改成符号名或引号内原文，并在开头写明这条约定与上面那次证伪。
符号名不会随改动漂移，原文可以检索。

#### 压缩参数是量出来的

同一段录屏压了五种参数，逐帧比对滚动途中与静止画面两种情况下的小字：

| 参数 | 体积 | 小字 |
| --- | --- | --- |
| `crf 20 / medium` | 16.1 MiB | 清晰 |
| `crf 24 / slow` | 12.1 MiB | 与上者无肉眼差别 |
| `crf 28 / slow` | **9.1 MiB** | 与上者无肉眼差别 |

#### 视频为什么不再进版本控制

交付压缩包里同时装着「工作树里这个文件」和「git objects 里那一份」，
**一份 9.1 MiB 的视频要占 18 MiB 的额度**；而历史里那份永远删不掉——
已经有一版 8.95 MiB 的旧视频留在 `a3acee6` 上，那正是本仓库要能复核的提交之一，不能动。

实测：视频保持 16.1 MiB 且进 git 时，压缩包 28.26 MiB；
按上表压到 9.1 MiB 之后，若仍进 git 则是 2×9.07 + 11.10（`.git` 现值）+ 1.0 ≈ **30.2 MiB，压着 30 MiB 的上限翻过去**。
把视频移出版本控制、仍随压缩包交付，落到约 **21 MiB**，留出可加东西的余量。

理由不止是省体积：这个视频现在是 `frontend/scripts/video/` 那条流水线的**产物**，
产物不需要版本控制，产出它的流水线才需要。这条已写进 `.gitignore` 的注释里。

### 十一、线上那个 500：用户写全了代码，产品反而崩了

上一节部署完，我从外部把交付材料里出现过的**几种标的写法**挨个打了一遍接口
（只写名称、只写裸代码、写全带后缀的代码），撞上这个：

```text
POST http://39.96.194.197/thesis/api/verify
{"raw_text": "我认为贵州茅台（600519.SH）的估值已经回落，但基本面并没有恶化"}

HTTP 500 Internal Server Error
```

同一句话，去掉括号里那段代码，返回 200 和一份完整结论。

#### 成因：认得代码，却把用户写的后缀丢了

解析层的 `_detect_subject` 用 `_CODE_RE` 认出「600519」，返回 `(code, None)`；
`parse_thesis` 把它当成 `ticker`。而用户明明写在那里的 `.SH` 没有任何一层去读。
于是构造出一个 **`ticker` 有值、`thscode` 为空**的 `ParsedThesis`，
撞上 `ParsedThesis` 自己的校验器——

> 给出了 ticker 就必须给出带交易所后缀的完整 thscode，不允许猜后缀

校验器抛 `ValidationError`，异常一路穿到 FastAPI，变成 500。
**校验器是对的**：它拦的正是「猜后缀」这件事。错的是解析层没有把用户写出来的后缀读进去。

#### 为什么第一轮审计没抓到

这条最该记。第一次线上复测用的是**不带代码**的命题（`我认为贵州茅台的估值已经回落…`），
一路 200，于是判定线上可用。而**产品的错误提示恰好教用户去写那段代码**：
识别不出标的时，界面上的原文是

> 请在命题中直接写明六位股票代码或带交易所后缀的代码（如 600519.SH）以避免歧义

也就是说，**产品让用户做的事，做了就崩**——而且是照着产品自己的提示做的。
一个「按提示操作」的正常用户，比审计者更容易撞上它。

#### 修法：两处

| 位置 | 改动 |
| --- | --- |
| `parse.py` | 新增 `_detect_thscode()`，读用户自己写出来的后缀（支持 `.` 与全角 `．`、大小写后缀）。**这不是猜后缀**，后缀是用户写的 |
| `parse.py` | 另一半兜底：只有裸 6 位代码时不再让 `ticker` 单独存在，而是清空 `ticker`、如实「不认标的」，把「没能确定标的」交给取数前的消歧段去报 |
| `run.py` | 命题里写全了代码时直接采信；同时把 `_detect_subject` 抽出的裸代码也交给检索接口**查**一次——这是查（接口按代码返回带后缀的 thscode），不是猜 |
| `run.py` | 标的已确定、只是没查到名称时，不再追加「未能确定标的」——此前无条件报错，于是写全了代码的命题会一边跑出结论、一边挂着一条自相矛盾的失败 |
| `run.py` | 同一次失败只报一条：消歧段的详细错误与它后面的兜底报的是同一件事，界面上会顶出两条 |
| 提示文案 | 只推荐带后缀的写法。裸代码能否解析取决于检索接口，不该在报错里当成可行建议 |

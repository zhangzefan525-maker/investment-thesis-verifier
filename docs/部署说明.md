## 一、为什么是子路径，不是独立端口

这台机器（阿里云 ECS，`39.96.194.197`）上**已经跑着另一个项目**
`literature-fingerprinting`：它占着 80 端口，nginx 里是一个 `server_name _`
的 catch-all，并且挂了一条每 2 分钟跑一次的自动部署 cron
（`/usr/local/bin/literature-autodeploy.sh`，只做 git 拉取 + 重启该服务）。

两点约束决定了方案：

1. **只有 80 端口在安全组里开着。** 实测 8080 / 8001 从外部访问是
   `Connection timed out`（安全组拦截），不是 `Connection refused`——
   也就是说本产品不能自己另起一个对外端口，除非去阿里云控制台改安全组。
2. 80 端口已被 catch-all 的 server 块占住。nginx 在同一个端口上按
   `server_name` 选块，而按 IP 访问时 `Host` 是 IP 本身，只会命中 `_` 那个兜底块——
   再加一个 `server_name` 块没用。

所以本产品挂在**子路径 `/thesis/`** 下：

```nginx
location = /thesis { return 301 /thesis/; }     # 补一道跳转，否则裸 /thesis 会掉进另一个项目

location /thesis/ {
    proxy_pass http://127.0.0.1:8001/;          # 结尾的斜杠是关键
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 180;
}
```

`proxy_pass` **结尾带斜杠**，nginx 会在转发前把 `/thesis` 前缀剥掉。
因此后端看到的仍然是 `/` 与 `/api/...`，**应用代码一行都不用改**——
不需要 `root_path`，不需要给路由加前缀。

对现有项目的改动仅限于：在它那个 server 块里**插入**上面这段，
原有的 `location /` 与其他指令一字未动。改前已备份、`nginx -t` 通过后才 reload。

## 二、前端为什么要重新构建一次

子路径部署的代价落在前端：`index.html` 里的资源引用和接口地址都是绝对路径，
不带上 `/thesis` 就会打到站点根上——**而且不会报错**，只会静默地
请求到另一个项目的路由里去。

所以：

- `vite.config.js` 的 `base` 改成读环境变量 `VITE_BASE`（默认 `/`）。
- 所有接口调用从写死的 `fetch('/api/...')` 改为 `fetch(api('/api/...'))`，
  由 `src/lib/api.js` 统一拼上 `import.meta.env.BASE_URL`。

**本地开发不受影响**：`VITE_BASE` 缺省是 `/`，`npm run build` 出来的就是
根路径版本，直接跑 `uvicorn` 打开 `localhost:8000` 一切照旧。
仓库里 `frontend/dist` 提交的也是根路径版本——评审拿到代码不装 Node 就能直接跑。

### 构建线上版本时的坑（已踩）

Windows 的 Git Bash 会把 `VITE_BASE=/thesis/` 当成 POSIX 路径，
自动转义成 `C:/Program Files/Git/thesis/`，于是构建出的资源路径变成
`/Program Files/Git/thesis/assets/...`——页面白屏，而且构建日志里看不出任何异常。

验证方式是构建完直接看引用：

```bash
grep -o 'src="[^"]*"\|href="[^"]*"' frontend/dist/index.html
# 正确：/thesis/assets/index-xxxx.js
# 踩坑：/Program Files/Git/thesis/assets/index-xxxx.js
```

线上构建命令（关掉路径转义）：

```bash
cd frontend
MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*' VITE_BASE=/thesis/ npm run build
```

Linux/macOS 上直接 `VITE_BASE=/thesis/ npm run build` 即可。

所以运行在实时模式（见下）。

## 四、线上当前是实时模式

`/api/health` 会如实回报这一点：

```json
{"status":"ok","credential":{"present":true,"origin":"用户级凭据文件 credentials.env"},
 "live_available":true,"fixtures":{...}}
```

界面顶部同时显示当前模式，所以登录进来的人一眼能看出数据是不是实时的。

**切回冻结快照模式**（一步，不需要改代码、不需要改 systemd 单元）：

```bash
ssh root@39.96.194.197 "rm /root/.config/hithink-finance/credentials.env"
```

反转条件：删掉之后 `/api/health` 的 `live_available` 变回 `false`，页面顶部的横幅
回到「冻结快照模式 · 非实时」，此时用 `backend/fixtures/` 下 44 份**对扶摇接口的
真实调用快照**（覆盖比亚迪、宁德时代、贵州茅台、中国平安 4 个标的）。

这是产品的既定行为，不是降级兜底：**没有凭据时不编造数据、不静默假装实时**，
而是说清楚哪些数字是快照、快照的截止时间、以及怎么切换成实时。
四个例题标的都在快照覆盖范围内，所以两种模式下演示都完整可用——
两种模式的结论逐字段一致，实测见 README「一、在线地址与本地运行」那张表。

### 配凭据的办法（本次就是这么做的）

**不需要重启服务。** `make_provider()` 与 `credential_status()` 都是**每次请求
现算**的：`FuyaoClient` 在构造时才调 `load_api_key()` 去读凭据文件。
所以文件落盘后的下一个请求就已经是实时模式了——这一点是实测确认的，
不是从代码推的：凭据文件落盘后**没有重启服务**，直接打 `/api/health`，
`live_available` 就从 `false` 变成了 `true`。
（同一轮里的代码部署重启过服务，那一步与凭据无关；这里说的是切模式这一步。）
反过来说，如果按老文档先 restart 再验证，就永远验不出「其实不用重启」这件事。

凭据文件放成根用户独占：

```bash
ssh root@39.96.194.197 "install -d -m 700 /root/.config/hithink-finance && \
  cat > /root/.config/hithink-finance/credentials.env && \
  chmod 700 /root/.config/hithink-finance && \
  chmod 600 /root/.config/hithink-finance/credentials.env" < <本地凭据文件>
```

三条纪律，都是为了 Key 不进任何可见的地方：

1. **走 stdin**（上面那个 `<`），不进命令行参数、不进 shell 历史、不进 `ps` 输出；
2. 目录 `700`、文件 `600`，只有 root 读得到；
3. 落盘后只校验**变量名与字符数**，不 `cat`、不 `echo`：

```bash
cut -d= -f1 /root/.config/hithink-finance/credentials.env     # 变量名
cut -d= -f2- /root/.config/hithink-finance/credentials.env | tr -d '\n' | wc -c   # 字符数
```

凭据不进仓库、不进部署包（`tar` 只打 `backend frontend docs README.md`），
所以**重新部署不会覆盖它**，也不用手动再配一次。

## 五、重新部署

### 先看这次改了什么：只动后端就不用重新构建前端

上面那套五步是**前端也变**时的全量流程。只改了后端（本次修 500 就是这样）时
不必走它：前端产物本来就没变，重新构建一次反而多一次把 `/thesis/` 版本
覆盖成根路径版本的机会。此时只打后端与文档：

```bash
tar --exclude='.git' --exclude='node_modules' --exclude='.venv' \
    --exclude='__pycache__' --exclude='.pytest_cache' --exclude='*.pyc' \
    -czf /tmp/tv.tar.gz backend docs README.md
tar -tzf /tmp/tv.tar.gz | grep '^frontend/' && echo '不该出现 frontend，中止'
ssh root@39.96.194.197 "cp -a /opt/thesis-verifier /opt/thesis-verifier.bak-\$(date +%Y%m%d-%H%M%S)"
scp /tmp/tv.tar.gz root@39.96.194.197:/tmp/
ssh root@39.96.194.197 "tar -xzf /tmp/tv.tar.gz -C /opt/thesis-verifier && \
  systemctl restart thesis-verifier && systemctl is-active thesis-verifier"
```

打包前顺手确认两件事：`tar -tzf` 里**没有** `frontend/dist`（不然白屏），
以及**没有**任何凭据文件（`tar` 只打仓库里的路径，凭据在 `/root/.config`，打不到）。
个别文件的小改动也可以直接 `scp` 那一个文件再 `systemctl restart`。

### 顺序是有讲究的：先构建线上版，再打包，最后把仓库那份拷回来

**仓库里的 `frontend/dist` 是根路径版本，线上要的是 `/thesis/` 版本。**
打包命令里带着 `frontend`，所以如果直接拿仓库现状打，就会把根路径的 `dist`
覆盖到线上，页面白屏——而且 `systemctl is-active` 照样是 `active`，
`nginx -t` 照样通过，**没有任何一步会报错**。

正确顺序（本节所有命令实测跑过）：

```bash
cd thesis-verifier

# 1. 本地构建**线上版**（关掉 Git Bash 的路径转义，见第二节）
cd frontend
MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*' VITE_BASE=/thesis/ npm run build
grep -o 'src="[^"]*"' dist/index.html     # 必须是 /thesis/assets/...，不是 /assets/...
cd ..

# 2. 打包（排除依赖、版本库与构建缓存；演示视频在仓库根目录，不进包）
tar --exclude='.git' --exclude='node_modules' --exclude='.venv' \
    --exclude='__pycache__' --exclude='.pytest_cache' --exclude='*.pyc' \
    --exclude='.vite' -czf /tmp/tv.tar.gz backend frontend docs README.md
tar -xzOf /tmp/tv.tar.gz frontend/dist/index.html | grep -o 'src="[^"]*"'   # 复核一次

# 3. 备份线上现有那一份，再解开
ssh root@39.96.194.197 "cp -a /opt/thesis-verifier /opt/thesis-verifier.bak-\$(date +%Y%m%d-%H%M%S)"
scp /tmp/tv.tar.gz root@39.96.194.197:/tmp/
ssh root@39.96.194.197 "
  tar -xzf /tmp/tv.tar.gz -C /opt/thesis-verifier
  /opt/thesis-verifier/backend/.venv/bin/pip install -q -r /opt/thesis-verifier/backend/requirements.txt
  systemctl restart thesis-verifier
  systemctl is-active thesis-verifier
"

# 4. 清掉上一版留下的资源文件（tar 只覆盖不加删除，旧 hash 的文件会一直积着）
ssh root@39.96.194.197 "cd /opt/thesis-verifier/frontend/dist/assets && \
  ls | grep -v -e 'index-DfUvD90v.js' -e 'index-Blr39DmE.css' | xargs -r rm -f && ls -la"

# 5. 把仓库那份 dist 构建回根路径版本，否则下一步 commit 会把线上版提交进仓库
cd frontend && npm run build && grep -o 'src="[^"]*"' dist/index.html && cd ..
git status --short frontend/dist      # 应当是空的
```

第 4 步的 hash 按当次构建结果替换——`ls` 出来的就是真名。

### 部署后必须从外部验一遍，而不是只看服务在跑

```bash
cd frontend
UI_BASE=http://39.96.194.197/thesis node scripts/ui-smoke.mjs
```

这条脚本会在真实无头 Chromium 里点一遍四条例题、三个 tab，
并检查零控制台错误与无 markdown 泄漏。**「服务在跑」不等于「站点是对的」**：
上面那个白屏的场景里，`curl /thesis/api/health` 会返回正常的 JSON，
只有从外面点一遍页面才会露出来。本次部署后已跑通。

### 回滚一次部署

```bash
ssh root@39.96.194.197 "
  rm -rf /opt/thesis-verifier && \
  cp -a /opt/thesis-verifier.bak-<上一步打印的时间戳> /opt/thesis-verifier && \
  systemctl restart thesis-verifier && systemctl is-active thesis-verifier"
```

## 六、回滚 nginx 配置（与第五节的「回滚一次部署」是两件事）

nginx 配置改前备份在 `/root/nginx-backups/`（用 `cp -L` 取的实体文件，
不是符号链接，校验过 md5 与线上一致）：

```bash
cp /root/nginx-backups/literature-fingerprinting.<时间戳>.conf \
   /etc/nginx/sites-available/literature-fingerprinting
nginx -t && systemctl reload nginx
```

停掉本产品：`systemctl disable --now thesis-verifier`。
两条操作都**不会影响** `literature-fingerprinting`——它的服务、端口、
cron 与自动部署全程未被触碰。
